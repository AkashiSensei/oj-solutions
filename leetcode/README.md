## Implementation index

Each accepted row is matched to the local solution code, excluding comments, includes, and local `main()` test code. All four performance values in a row come from the same submission-detail page or accepted-submission screenshot, not the rounded submission list. Each source file also contains a matching English `Submission Record` in its problem-header comment. In the Runtime and Memory cells, the first line is the measured value and the second line is the analyzed complexity. For islands, `m` and `n` are the grid dimensions and `L` is the number of land cells. For one-dimensional array and string problems, `n` is the input length. Space complexity describes auxiliary storage excluding input copies; LC 3 takes its string by value, so an lvalue call also creates an O(n) input copy, as noted in its source comment. LC 739 uses up to O(n) stack entries, excluding its O(n) returned answer array. For `739-array.cpp` and `739-array-day.cpp`, `C = 100005` is the fixed global stack capacity: each buffer reserves O(C) auxiliary storage even when only O(n) entries are used. The former stores two integers per entry; the latter stores only the day index. For `146.cpp`, `U = 10001` is the direct-address table length and `C = 3001` is the reserved list-slot count. Each cache object reserves O(U + C) storage and takes O(U + C) construction time to zero-initialize its arrays. Each `get` and `put` takes O(1) worst-case time; q operations including construction take O(U + C + q). The arrays are per-instance members, not shared globals. For `146-stl.cpp`, `c` is the configured capacity. The unordered map and list use O(c) auxiliary space. Each get/put takes average/amortized O(1) time, with O(c) worst-case time; moving an existing list node with splice is O(1) and preserves its iterator. Empty-container construction takes O(1) time. For `98.cpp`, `n` is the tree node count and `h` is the tree height. Recursive DFS takes O(n) worst-case time and O(h) auxiliary stack space, which is O(log n) for balanced trees and O(n) for skewed trees. For `215.cpp`, each partition is in place, but the fixed first-element pivot and one-sided handling of equal values can produce O(n²) worst-case time and O(n) recursion stack space. Balanced shrinking intervals give O(n) time and O(log n) stack space; this version has no randomized expected-time guarantee. For `215-three-way.cpp`, equal values are grouped and excluded together, making all-equal inputs O(n) time with O(1) recursive depth. Its pivot is still fixed, so distinct-value extreme partitions can still cause O(n²) time and O(n) stack space; balanced shrinking intervals give O(n) time and O(log n) stack space. For `215-counting.cpp`, `U = 20002` is the counting-buffer length (20001 valid value buckets plus one unused zero slot). Initialization and the descending scan take O(U) time, counting takes O(n), and auxiliary space is O(U), for O(n + U) total time. The bounded value range makes U constant with respect to n; each call creates fresh counters and leaves the input unchanged. For `347.cpp`, `U = 20002` is the counting-buffer length and `d` is the number of distinct input values. Counting and the full bucket scan take O(n + U). Inserting all d nonzero buckets into the max heap individually takes O(d log(d + 1)); extracting k records takes O(k log(d + 1)). Since k <= d, total time is O(n + U + d log(d + 1)), with O(U + d) auxiliary storage excluding the O(k) returned answer. The final buffer slot is unused. Under the fixed value range, d <= 20001 and U is constant, so time is O(n) and auxiliary space is O(1) with respect to n alone. For `347-min-heap.cpp`, `d` is the number of distinct values. Hash-table counting takes average/amortized O(n) time, processing distinct values with a heap of at most k records takes O(d log k), and extracting the answer takes O(k log k). Since k <= d, total average/amortized time is O(n + d log k); severe hash collisions can increase the total to O(n*d + d log k) in the worst case. Auxiliary space is O(d + k), excluding the returned answer. The log k bounds assume k >= 2; when k = 1, heap operations take O(1), processing candidates takes O(d), and total average/amortized time is O(n). This version requires C++17 for structured bindings. For `23.cpp`, `N` is the total input node count, `k` is the number of input lists, and `U = 20001` is the counting-buffer length. Visiting all list heads and nodes takes O(k + N), including empty lists; counter initialization, the bucket scan, and output construction take O(U + N), for O(k + N + U) total time. Auxiliary space is O(U), excluding O(N) newly allocated output nodes; including the output, allocated storage is O(U + N). Input nodes are not modified or reused. The heap-allocated dummy head is not released in this version, and the local main also leaves output nodes unreleased. With the fixed value range, U is constant, giving O(k + N) time and O(1) auxiliary space. For `23-heap.cpp`, `N` is the total input node count, `k` is the number of input lists, and `m` is the number of non-empty lists. The min heap stores at most m pointers, one candidate per original list. Scanning all list heads costs O(k), and each node is inserted and removed once, giving O(k + N log k) time for k >= 2. For k <= 1, heap operations take O(1) each and total work is O(k + N), with O(1) work for empty input. Auxiliary space is O(k), more precisely O(m) heap pointers plus a temporary dummy node. Output nodes are reused by modifying input next links; no O(N) output nodes are allocated. The dummy node is deleted before returning. For `207.cpp`, `V = numCourses` and `E = prerequisites.size()`. Course initialization and initial queue seeding take O(V); adjacency construction takes amortized O(E). Each course is queued at most once and each prerequisite edge is processed once, giving O(V + E) total time. Auxiliary space is O(V + E) for course records, adjacency lists, and a queue of course IDs; there is no recursive stack. The prerequisite input is not modified. For `743.cpp`, `V = n` and `E = times.size()`. This min-heap Dijkstra version stores a settled flag per node but no tentative-distance array. Each newly settled node pushes candidates for all its outgoing edges, including edges to already settled targets; duplicate entries are discarded when popped. Every reachable edge is expanded once, so at most E + 1 heap records are inserted and removed. Total time is O(V + E log E), with constant-time heap work when E = 1, and auxiliary space is O(V + E) for adjacency lists, settled flags, and an O(E) candidate heap. Since the graph has no parallel edges, E <= V*(V - 1), giving the alternative bound O((V + E) log V) for V >= 2. Only a newly settled node updates the returned distance, preserving the last finalized shortest distance when stale entries are discarded. The local main retains the user-provided regression case before the official examples. For `743-dist.cpp`, a tentative-distance array filters candidates before insertion: only a strictly shorter discovered path is queued, and dist is updated immediately. A rejected candidate cannot improve any continuation beyond its target because a path with no greater cost to the same target has already been queued or processed. Settled flags still discard old heap entries. At most E successful relaxations create new records, so worst-case time remains O(V + E log E), with constant-time heap operations for E = 1, and auxiliary space remains O(V + E). The additional dist array uses O(V) space; actual heap insertions and peak heap size can decrease, while the worst-case bounds are unchanged. For graphs without parallel edges, O((V + E) log V) is an alternative time bound for V >= 2. For `743-scan.cpp`, initialization takes O(V), adjacency construction takes amortized O(E), and at most V full scans of V node IDs take O(V^2). Each reachable edge is relaxed once, giving O(V^2 + E) worst-case time. Auxiliary space is O(V + E) because this implementation retains adjacency lists rather than an adjacency matrix. The by-value construction loop copies each three-integer edge vector, adding per-edge copy/allocation overhead without changing the asymptotic bound. Input times is not modified, and the regression case remains first in main. For `743-scan-ref.cpp`, the only executable-code change from `743-scan.cpp` is using `const auto& edge` in the adjacency-construction loop. This avoids copying and allocating a temporary three-integer vector per input edge. Time remains O(V^2 + E), and auxiliary space remains O(V + E). The 76 ms / 43.31 MB screenshot is recorded separately from the earlier by-value submission. For `743-heap-ref.cpp`, the only executable-code change from `743.cpp` is reading input edges by const reference during adjacency construction, avoiding a temporary vector copy and allocation per edge. The candidate-heap behavior is unchanged, so worst-case time remains O(V + E log E) and auxiliary space remains O(V + E). Its latest matching accepted screenshot records 88 ms and 45.45 MB.

## Recording rules

- Record the latest accepted submission that matches the repository version, not the best runtime or memory selected from unrelated submissions.
- Keep the implementation filename, approach, language, status, runtime, memory, both beat percentages, and observation date in the index. Keep submission timestamps and links in each source file's `Submission Record`, not in the index table.
- Sort accepted rows by submission time, earliest first, rather than problem number or performance.
- Keep source comments and this index consistent. Comments describe the current implementation; retain earlier submission rows and source commits as history.
- For later additions, append a row to the index table. If a solution changes and is resubmitted, append another row and update its source comment with the matching result.
- Add an implementation only after it is complete and a matching submission is accepted. Keep unfinished frameworks out of the index. For unavailable metrics on accepted submissions, use `N/A`; never invent values or substitute zero.
- Beat percentages are LeetCode's displayed comparisons for the same problem and language; higher is better. They are not an absolute rank or contest rating and can change after the submission date.
- These are individual judge-run snapshots, not stable benchmark results. A displayed runtime of `0 ms` does not mean zero execution time. Compare language, algorithmic complexity, and judge variation before interpreting small differences.
- This index covers LeetCode solutions. Codeforces has a separate judging system and is not mixed into these percentages.
